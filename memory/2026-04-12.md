
## Notion database/schema workflow fix

- Important Notion API lesson: creating a database via `POST /v1/databases` may successfully create the visible database shell while silently leaving the underlying data source with only the default `Name` property.
- The reliable fix path is:
  1. create the database shell first,
  2. read the returned `data_sources[0].id`,
  3. patch the schema on the **data source** itself via `PATCH /v1/data_sources/{data_source_id}`,
  4. then create rows/pages using the database id.
- Patching the database shell alone can appear to succeed while not materializing the columns in Notion UI.
- This exact issue was hit again while creating the shared movie-watch database for Josh and Clara. The working version was the one where the schema was patched on the data source and then seeded.
- Useful heuristic: when Notion says the database exists but only the Name column appears, inspect the data source properties, not just the database object.
- Product judgment: a dedicated Notion-specialist subagent could help if it carries a small durable playbook for these API quirks, but a full memory-isolated agent is probably overkill right now. Better near-term move is a short local runbook/skill note with the exact create -> data_source patch -> seed sequence.
